What we found

Fix now Accounts without multi-factor authentication ▸

5 active accounts have no MFA enabled.

These accounts can be signed into with a password alone. A single phished, guessed, or reused password is all an attacker needs -- no second factor stands in the way. This is the single most common way small practices get breached, and multi-factor authentication would stop nearly all of it at the front door. Worse, 1 of these is an administrator account (Dr. Marcus Reyes <mreyes@cypresseye.example>), so compromising one hands an attacker control of the entire environment.

Affected

  • Tyler Brooks (Front Desk) <tbrooks@cypresseye.example>
  • Former Receptionist <frontdesk2@cypresseye.example>
  • Temp Scanner Account <scanner@cypresseye.example>

How to fix it

  1. Require MFA for every user, administrators first.
  2. Prefer an authenticator app or hardware key over SMS codes.
  3. Enforce it with a conditional-access policy (or security defaults) so new accounts get it automatically.

Fix this week Stale / orphaned active accounts ▸

2 active accounts look abandoned but still enabled.

Each of these accounts is still enabled but shows no recent use -- the classic signature of a staff member who left without their access being turned off. Every one is a standing door into the practice that nobody is watching: it can be taken over quietly, and because no one uses it, the misuse goes unnoticed for months.

Affected

  • Former Receptionist <frontdesk2@cypresseye.example> (last signed in 249 days ago)
  • Temp Scanner Account <scanner@cypresseye.example> (has never signed in)

How to fix it

  1. Confirm whether each account belongs to someone who still works here.
  2. Disable (don't delete) departed-staff accounts immediately, then remove them after any required retention period.
  3. Put a written termination checklist in place so access is revoked the day someone leaves.

Fix this week Too many administrator accounts ▸

3 accounts have full administrator rights (recommended maximum for a practice this size is 2).

Full administrator rights should be rare -- an admin account can change security settings, read anyone's mail, and reset passwords. The more accounts hold that power, the bigger the target: an attacker only has to phish one of them to own everything. Day-to-day work almost never needs admin rights.

Affected

  • Dr. Marcus Reyes <mreyes@cypresseye.example>
  • Dana Whitfield (Office Manager) <dwhitfield@cypresseye.example>
  • Kevin Osei (IT contractor) <kosei@cypresseye.example>

How to fix it

  1. Keep two administrator accounts (one primary, one break-glass backup) and remove admin rights from everyone else.
  2. Give staff only the specific permissions their job needs (least privilege).
  3. Require admins to do everyday work from a normal, non-admin account.

Fix this week Baseline security protections are turned off ▸

Security defaults (the free baseline protections) are disabled.

The platform's built-in baseline -- which enforces MFA, blocks the weakest legacy sign-in methods, and protects admin actions -- is switched off. With it off, the practice is relying on protections that have to be configured by hand, and the gaps found in this report are the predictable result.

Affected

  • Tenant-wide setting

How to fix it

  1. Turn on security defaults (or, if you've outgrown them, replace them with equivalent conditional-access policies).
  2. Confirm MFA is enforced for all users afterward.

Fix this month Outdated sign-in methods are still allowed ▸

Legacy authentication protocols are still permitted.

Old sign-in methods (legacy authentication) can't do multi-factor authentication, so attackers use them as a side door to bypass MFA entirely. They're a favorite target of automated password-spray attacks and are almost never needed by a modern practice.

Affected

  • Tenant-wide setting

How to fix it

  1. Block legacy authentication tenant-wide.
  2. Move any old device or app that depended on it to a modern, MFA-capable sign-in method first.

Fix this month External / guest accounts with standing access ▸

1 external guest account has access to the environment.

These accounts belong to people outside the practice -- a billing contractor, a former vendor, an outside consultant. Outside access is sometimes legitimate, but each account is a door you don't fully control, and standing access that outlives its purpose is a common blind spot. If any of these people handle patient data, a signed business associate agreement is legally required.

Affected

  • OutsourceBill LLC (billing vendor) <ap@outsourcebill.example>

How to fix it

  1. Review each guest: confirm who they are and whether they still need access.
  2. Remove access that is no longer needed.
  3. Make sure a signed business associate agreement is on file for any outside party that touches patient data.
